    Models¶

    A model is a Pydantic class that describes what a dataset is: its columns, where it lives and how it is stored. Model.objects then reads and writes the dataset as Polars DataFrames, validated against the model.

    from datetime import datetime
from smallcat import Model, ModelFileFormat, ModelWriteMode

class Customer(Model):
    id: int
    name: str
    email: str | None = None
    created_at: datetime

    class Meta:
        location = "silver/customers"
        file_format = ModelFileFormat.PARQUET

    A model does not say which connection it uses. That is decided when it is registered, outside the model, so the same model runs against different storage in each environment.

    import polars as pl
from smallcat import Connections, registry

registry.load_connections(Connections.from_yaml("connections.yaml"))
registry.register(Customer, connection="lake")

Customer.objects.filter(pl.col("id") > 10).all()
Customer.objects.save(df, mode=ModelWriteMode.OVERWRITE)

    A complete, runnable example is in Models on the local filesystem, and the connection step is explained in Connections with the ORM. For filtering with filter, where, all and lazy, see Querying models.

    Meta¶

    Meta is validated when the class is defined, so a mistake fails on import and not on the first read. Unknown attributes are rejected and every problem is reported together.

    Attribute Required Description
    location yes Path of the data, relative to the connection's base.
    file_format yes A ModelFileFormat: CSV, EXCEL, PARQUET or DELTA_TABLE. The string ("parquet") is accepted too. Any other value is rejected, listing the valid ones.
    allowed_write_modes no The write modes the model permits. By default all of them. [] makes the model read-only.
    validation_mode no ModelValidationMode.STRICT (default) or COERCE. See Validation.
    load_options no Format options applied when reading.
    save_options no Format options applied when writing.

    load_options and save_options are the options each format already accepts in a catalog (sep, header, sheet, hive_partitioning, partition_by...) and are validated against the same schemas. They configure the file format, not permissions. For Delta tables the write mode cannot be set there: it is chosen on every save.

    A Meta is inherited by subclasses. A class without a Meta is abstract and cannot be registered.

    Field types¶

    The fields give the expected Polars types.

    Python type Polars type
    int, float, str, bool, bytes Int64, Float64, String, Boolean, Binary
    datetime, date, time, timedelta Datetime("us"), Date, Time, Duration("us")
    Literal["a", "b"], Literal[1, 2] String, Int64
    Enum (StrEnum, IntEnum, or any Enum whose values are all str or all int) String, Int64 (the member's value is stored)
    list[T] List(T)
    T \| None T, and the field accepts nulls

    Any other type (dict, nested models, unions of several types, Decimal...) is rejected with ModelDefinitionError when the class is defined, naming the field. Columns are matched by field name; aliases are not used.

    NaN is stored as None¶

    pandas hands empty cells over as NaN (an Excel sheet with blanks, for instance). A NaN given to a field that admits None (T | None) is stored as None, so you do not need a validator of your own:

    class Customer(Model):
    id: int
    email: str | None = None
    score: float | None = None


Customer(id=1, email=float("nan"), score=float("nan"))
# Customer(id=1, email=None, score=None)

    A field that does not admit None is never changed: a NaN in a plain float is a valid value and is kept. To keep the NaN in the nullable fields too, set nan_as_none = False on the model (it is inherited by subclasses). DataFrames are not affected: they keep Polars semantics, where empty cells are nulls and a real NaN in a float column is a valid value that all() keeps. Reading with all(as_models=True) builds instances, so there a NaN in a T | None field does become None.

    Types a file format cannot hold¶

    Having a Polars type does not mean every file format can store it. time and timedelta are the two that cannot, in some formats or in all of them. This was checked by writing and reading each one in each format:

    Field type parquet delta_table csv excel
    time yes no yes no
    timedelta no no no no
    every other type in the table above yes yes yes yes

    Why they fail:

    • Parquet and timedelta. DuckDB writes the duration as an INTERVAL and Polars cannot read that back: the process aborts with a PanicException.
    • Delta Lake has no time-of-day type and no duration type.
    • CSV and Excel have no duration type, and Excel has no time-of-day type either: the value comes back as a time or as text, not as what was written.

    A model that declares one of these combinations is refused when the class is defined, not when a job runs. The error names every field, says why and what to do instead:

    ModelDefinitionError: Job has fields its file format cannot hold:
  - Job.took is a timedelta, which cannot be stored in delta_table: Delta Lake
    has no duration type. Store it as a number (seconds as a `float`, or
    microseconds as an `int`) and convert it in your code.

    A list of those types (list[time]) is checked the same way, and so is an optional one (timedelta | None).

    One exception: Parquet written by another tool

    A timedelta in a Parquet file written by pyarrow or Polars is read without trouble. A read-only model (allowed_write_modes = []) may declare it over such a file, and all() and filter() work. where() does not: DuckDB gives the value back as a number.

    Registering¶

    registry.load_connections(Connections.from_yaml("connections.yaml"))
registry.register(Customer, connection="lake")
    • The connection must already be loaded (see Connections), otherwise ConnectionNotLoadedError lists the names that are.
    • Registering twice raises ModelRegistrationError, unless replace=True.
    • Using a model that is not registered raises ModelNotRegisteredError, which shows the call to make.
    • smallcat.registry is the default registry, shared by the whole process.

    Restricting what a model may do, per environment¶

    allowed_write_modes can be narrowed when registering, never widened. A model that is read-write in development can be made read-only in production without changing its code:

    registry.register(Customer, connection="lake", allowed_write_modes=[])

    Asking for a mode the model's Meta does not allow raises ModelRegistrationError.

    Tests and other registries¶

    Model.objects uses the current registry. use_registry replaces it inside a block and restores the previous one on exit, even on an exception. It is kept per context, so threads and async tasks do not affect each other.

    from smallcat import ModelRegistry, use_registry

test_registry = ModelRegistry()
test_registry.load_connections(Connections.from_dict(
    {"connections": {"lake": {"conn_type": "fs", "extra": {"base_path": str(tmp_path)}}}}
))
test_registry.register(Customer, connection="lake")

with use_registry(test_registry):
    Customer.objects.save(df, mode=ModelWriteMode.OVERWRITE)

    Reading¶

    Model.objects reads the dataset as a Polars DataFrame or LazyFrame, or as a list of validated model instances, and filter(), where() and select() choose the rows and fields:

    Customer.objects.all()                              # pl.DataFrame
Customer.objects.filter(pl.col("id") > 10).all()
Customer.objects.all(as_models=True)                # list[Customer]
Customer.objects.where(id__gt=10).all(as_models=True)

    The methods, every way of filtering, the operators, lazy reads and what is refused are in Querying models.

    Writing¶

    Customer.objects.save(df, mode=ModelWriteMode.OVERWRITE)
Customer.objects.save([Customer(...), Customer(...)], mode="overwrite")
Customer.objects.save(Customer(...), mode=ModelWriteMode.APPEND)

    save takes a DataFrame, an instance of the model or a list of instances (a LazyFrame must be collected first). The mode is required and has no default (except in instance.save(), see Saving one instance), because it decides what happens to the data that is already there:

    ModelWriteMode Effect Supported by
    OVERWRITE Replaces the whole dataset with the data you pass. csv, excel and parquet (a single file), and delta_table
    APPEND Adds the rows to what exists. delta_table only
    MERGE Inserts the rows whose key is new and updates the ones whose key already exists. It never deletes. delta_table only

    Saving one object with OVERWRITE leaves a dataset of one row; use MERGE to upsert it by key.

    Merging by key¶

    MERGE needs to know which fields identify a row. Declare them in Meta, or pass them in the call (the call wins):

    class Customer(Model):
    id: int
    name: str
    email: str | None

    class Meta:
        location = "silver/customers"
        file_format = ModelFileFormat.DELTA_TABLE
        merge_keys = ["id"]                    # optional

Customer.objects.save(df, mode="merge")                         # uses Meta.merge_keys
Customer.objects.save(df, mode="merge", merge_keys=["email"])   # replaces them
    • The keys are never updated. Matching rows get every other column of the data, or only the ones in save_options.update_columns (set it in Meta.save_options). New rows are inserted whole.
    • If the table does not exist, the first merge creates it.
    • The keys must be fields of the model, without repeats, and Meta.merge_keys must not be nullable (X | None): a key has to identify a row. This is checked when the model is registered.
    • The data must not have null or repeated keys: smallcat refuses it before writing instead of letting Delta fail ambiguously. It does not deduplicate.
    • The columns of the data must already exist in the table: a merge does not change the schema.
    • merge_keys with a mode other than merge is an error, not ignored. In a catalog, merge_keys or update_columns without mode: merge is refused when the catalog is loaded, not when it first saves. A model without keys can be registered; it fails when it is saved with merge without merge_keys.
    • allowed_write_modes includes merge by default; restrict it like the other modes.
    • Rows are not deleted by a merge (deleting by predicate is a separate issue, #32).

    A mode that is not a ModelWriteMode raises ValueError listing the valid ones. These cases are refused before anything is written:

    Error Cause
    ModelWriteNotAllowedError The mode is not in allowed_write_modes, or the model is read-only.
    ModelUnsupportedWriteModeError The format cannot do it: APPEND or MERGE on a file, or OVERWRITE on partitioned Parquet.
    ModelQueryError MERGE without keys, merge_keys with another mode, or a key that is not a field of the model.
    ValueError The data has null or repeated merge keys, or columns the Delta table does not have.
    ModelRegistrationError (when registering) Meta.merge_keys or update_columns name fields that do not exist, or the keys are empty, repeated or nullable.
    ModelSchemaValidationError The data does not match the model. See Validation.

    Partitioned Parquet cannot be overwritten

    With partition_by, DuckDB only adds files and keeps the old ones, so an "overwrite" would silently leave old partitions behind (this was checked: 3 rows plus 1 gave 4). OVERWRITE is therefore refused for a Parquet model whose save_options has partition_by. Use a Delta table, or write without partition_by.

    Validation¶

    A DataFrame is checked against the model on every read (all, as_models, lazy, where) and every write.

    Check STRICT COERCE
    A column is missing error error
    A column the model does not declare error (see below) error (see below)
    A column's type must be the declared kind: any integer width for int, any time unit or time zone for datetime... Nothing is converted cast to the declared type
    A value that cannot be cast n/a error
    A float that would lose decimals as int (42.7) n/a error
    A null in a field that is not X \| None error error

    validation_mode is set in Meta and applies to reads and writes alike. COERCE suits sources whose columns arrive as text, such as CSV; STRICT is the safer default for what you persist.

    Unexpected columns follow Pydantic's own setting: an error by default, dropped with model_config = ConfigDict(extra="ignore"), kept with extra="allow".

    All problems are reported together and never include the values, so a failed validation cannot leak data into a log:

    # STRICT
ModelSchemaValidationError: Customer does not match its schema:
  - id: expected Int64, got String
  - email: column is missing
  - extra: unexpected column

# COERCE
ModelSchemaValidationError: Customer does not match its schema:
  - id: 1 value(s) cannot be cast to Int64
  - created_at: 2 value(s) cannot be cast to Datetime(time_unit='us', time_zone=None)
  - name: 1 null value(s) in a required field

    The error has an issues list (column and problem) for programmatic use.

    Pydantic validates values (constraints, validators) when instances are built (save([Customer(...)]), as_models()). A DataFrame is checked for columns, types and nulls only, not row by row.

    Errors¶

    All inherit from ModelError.

    Error Raised when
    ModelDefinitionError Meta is invalid or a field type is not supported (on defining the class).
    ModelRegistrationError A model without Meta, registered twice, or asking for more write modes than Meta allows.
    ModelNotRegisteredError A model is used before being registered.
    ModelQueryError filter with where, where twice, an invalid select, as_models with select...
    ModelWriteNotAllowedError The write mode is not permitted.
    ModelUnsupportedWriteModeError The format cannot write with that mode.
    ModelSchemaValidationError The data does not match the model.

    Models and the catalog¶

    Models are built on the catalog: each registered model becomes a catalog entry internally, so it reads and writes through the same datasets, options and credentials. The Catalog is still the right tool for datasets defined in YAML or an Airflow Variable without code, and it does not validate columns. A model adds typed columns and validation, and lives in code.
